## 확정한 코드 원인 및 수정

1. `models.location()`이 요청 카테고리를 실제 분류처럼 저장했다.
   API `categories[].top_level_category` 기반으로 변경. 없는 분류는 null.
   호텔명/음식점명으로도 분류를 추측하지 않는다.
2. 실제 분류와 요청 분류의 불일치를 검사하지 않았다.
   알려진 분류가 요청과 다르면 전체 수집을 중단해 후속 소모를 방지한다.
3. 서로 다른 카테고리에서 동일한 장소 목록을 받은 상황을 감지하지 않았다.
   기존 캐시를 비교해 반복 결과가 있으면 일반 수집을 차단하고 진단을 안내한다.
4. 서버 오류 본문 및 리뷰 페이지/제공 범위 메타데이터를 버렸다.
   필요한 진단 필드만 선택하고 키를 제거해서 보존한다. HTTP 400을 권한 문제로 단정하지 않는다.

## 아직 확정할 수 없는 원인

- 서버가 카테고리별로 동일한 목록을 반환한 이유.
  현재 공식 문서는 category=ATTRACTION/HOTEL/RESTAURANT를 안내하며 구현도 이를 전송한다.
  요청 규격과 실제 서버의 불일치, 서버 설정 등은 비교 응답으로 확인해야 한다.
- 남구 bbox HTTP 400의 이유.
  기존 좌표의 남북/동서 순서는 유효하지만 서버가 반환한 검증 오류를 저장하지 않았다.
  넓은 범위가 원인일 가능성은 가설이며 확정된 사실로 취급하지 않는다.
- 리뷰 제공량이 장소당 0~1개인 이유.
  현재 파서는 빈 data에서만 빈 결과를 만들며 HTTP 오류/스키마 오류는 별도로 처리한다.
  원 응답의 pagination과 language_meta가 없어 계약 범위/페이지 동작을 구분할 수 없다.
  3개는 요청 상한이며 항상 3개가 제공된다는 뜻은 아니다.

## 원본 보존 및 검증

수정 작업에서는 실제 API를 호출하지 않고 기존 output 데이터/캐시/65 entity 원장을 보존한다.
테스트는 소켓 연결을 차단한 가짜 응답으로 수행한다. 기존 잘못된 카테고리 값을 사실로
재사용하지 않지만, 원본 파일은 감사 및 복구를 위해 그대로 둔다.

`--diagnose --dry-run`은 네트워크 호출 없이 계획만 출력한다. 사용자가 이후 진단 실행을
승인하면 현재 데이터 기준 최대 4회/16 entities, 재시도 0회로 비교 자료를 확보할 수 있다.
진단은 캐시/결과를 교체하지 않고 별도 메타데이터 보고서만 생성한다.
